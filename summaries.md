# Skill File Index

This file is the canonical inventory of the skill. Every file in the skill folder is listed below with its purpose and when to read it. Keep it in sync when adding, removing, or renaming files.

* "summaries.md": "This file. Canonical index of every file in the skill and when to read each one. Linked from SKILL.md and POWER.md; useful when entering mid-skill or needing the full file map."

* "SKILL.md": "Main entry point (Agent Skills format). Opens with the Go thesis - that Go module dependencies have no architecture dimension, so the Java/Python dependency-availability phase collapses and the four real failure classes are cgo, amd64-only build constraints and assembly, non-Go artifacts, and behavioral differences that compile cleanly. Contains scope guardrails, entry/exit criteria, the transformation checklist with phase routing, test and race failure handling, and the documentation output mapping. Read this first."

* "POWER.md": "Main entry point (Kiro Powers format). Same body as SKILL.md with Kiro-specific frontmatter (displayName, keywords, author). Regenerate with scripts/sync_power.sh after editing SKILL.md."

* "phases/phase1-static-analysis.md": "Detailed steps for Phase 1: project structure analysis (every build system present and which one ships, module vs workspace vs vendor layout, Go version with its four disagreeing sources, target OS, glibc-vs-musl and kernel page size, and the two-pass `go list` capture - reachable packages plus a per-directory sweep, both with CGO_ENABLED=1, because a package nothing imports is silently skipped by `./...` and CgoFiles is empty when cgo is off); the cgo inventory with the four library routes; the build-constraint and assembly analysis across the module AND vendor/, classified into three shapes; non-Go artifact and build-configuration detection (committed binaries by content, downloaded tools, image platforms from their registries, GOAMD64, GoReleaser, deployment descriptors that select x86 by being absent); the behavioral scan (race priors, x86 CPU gates, syscall numbers and seccomp, page size, FMA-sensitive floats, CGO_ENABLED-driven resolver behavior); and the Go version check with its arm64-relevant floors."

* "phases/phase2-resolution.md": "Detailed steps for Phase 2: cgo resolution per route (per-architecture `#cgo` directives, aarch64 system packages verified against the target distro's index without emulation, the bundled-archive version upgrade that is the one dependency change this skill endorses, and the BLOCKER-as-user-decision template); build-constraint resolution in three fixes with the filename-suffix trap that silently defeats a widened `//go:build` line; native artifact re-sourcing with architecture-derived download URLs; build configuration including the cross-compiling multi-stage Dockerfile pattern that is Go's structural advantage over Java and Python, GOAMD64/GOARM64 handling, GoReleaser docker_manifests, the arm64 CI matrix leg, and every deployment descriptor; behavioral fixes with the explicit list of non-fixes for a data race; and the documented Graviton runtime recommendations with evidence levels."

* "phases/phase3-validation.md": "Detailed steps for Phase 3: the table of what each environment can prove (cross-compile executes nothing; emulation is not the race check); working container runtime detection; Go toolchain alignment, session-scoped; the three escalating build steps ending in the deployment's own release command; the INFRA/ARM64/PRE-EXISTING classification with the x86 baseline that makes it possible; the recognizable failure messages, three of them captured verbatim from a deliberately broken fixture; `go vet` as a diff against the baseline; the plain test run and the mandatory separate race run with its repetition strategy and its x86 comparison; results that change without failing; container validation including a scan of every native file inside the image; startup validation with a misleading-symptom table; and the summary rules."

* "document_references/agent-scope-boundaries.md": "CRITICAL guardrails. MUST be read before starting. Opens with the Go-specific trap - that 'does version X support arm64' is a malformed question for a Go dependency and an agent carrying Python or Java reflexes will produce a report full of version bumps that have nothing to do with arm64. Contains the seven-question decision tree, the IN SCOPE / OUT OF SCOPE definitions, the should-I-update-this-dependency tree whose most common leaf is 'do not touch it', the recommendation validation ladder, the verified non-issues in Go (including that AArch64 on Linux is little-endian), fourteen red flags, the documentation templates for changes made and changes deliberately not made, and five case studies drawn from real failure modes."

* "document_references/cgo-and-native-dependencies.md": "Evidence standard for every verdict in 02-cgo-report.md. The four routes a C library takes into a Go build and why conflating them produces wrong verdicts; how to establish which route applies; the per-route method with its evidence (unguarded x86 intrinsics in vendored C, the target distro's aarch64 index queried without emulation, the ar/file sequence on a bundled archive, the release asset listing); commonly-hit modules with the check to run rather than asserted version floors; cross-compiling cgo and why a native arm64 builder is usually the better answer; glibc, musl and static linking; the CGO_ENABLED escape hatch and the four things it changes including disabling the race detector; and nine false verdicts. Read during Phase 1.2 and whenever a cgo verdict needs backing."

* "document_references/build-constraints-and-assembly.md": "Evidence standard for every verdict in 03-build-constraint-report.md. How Go decides which files to build, including that the filename suffix overrides a `//go:build` line - the mistake that makes a Shape C fix a no-op; the two-pass authoritative detection with the measured table showing that `./...` reports zero errors for an unimported amd64-only package in `go list`, `go build` AND `go vet`; the three shapes and why the count is meaningless; four variants of Shape C in disguise; how to read a fallback implementation, with the stub-and-panic patterns that pass the build and return wrong answers; the assembly inventory and what its counts mean; the build tags projects offer for a portable path and the global cost of using one; the x/sys/cpu feature bit mapping for Graviton; and ten false verdicts. Read during Phase 1.3."

* "document_references/behavioral-differences.md": "Evidence standard for 05-behavioral-findings.md - the findings that compile cleanly and reach production. The memory model, with the precise framing that arm64 reveals races x86 hides rather than breaking racy code, how to find them, and the explicit list of non-fixes; FMA fusion with the specification's own wording and the three ways to resolve a test that depends on non-fused arithmetic; syscall numbers with the arm64 substitution table and the silent numeric-seccomp case including which direction it fails; page size graded per distribution, with the table separating page-granular uses from innocent ones; CPU feature dispatch where the finding is always the final else; cgo-dependent net and os/user; core count and SMT and the sizing assumptions that go stale; ten claims that are the same on both architectures and are often asserted otherwise, led by the endianness myth; and ten false verdicts. Read during Phase 1.5."

* "document_references/module-management-mapping.md": "Detection markers and per-build-system commands for go build, Makefile, GoReleaser, Bazel with rules_go, ko, Docker and buildx, AWS Lambda on provided.al2023, and the four CI systems - plus modules, vendor and workspaces, and private module proxies. Includes the command table per phase, the vendor rules (scan it, re-vendor after a change, never hand-edit it), the workspace rule (run from go.work's directory or you analyse a tree that does not ship), the Bazel caveat that go list may not see the real dependency set, the Lambda two-places-to-set-the-architecture trap, and the GitHub Actions matrix that makes the arm64 race check permanent. Read in Phase 1.1 and whenever a step needs a specific system's command."

* "document_references/documentation-standards.md": "Defines the mandatory graviton-validation/ output folder, the canonical filenames (00-summary.md through 07-build-test-results.md plus raw/), and the required sections of each file with a worked template. Two properties every file must have: every verdict cites its evidence, and every result names the environment it came from. Includes the full 00-summary.md template with its exit-criteria table and headline block, and the raw-file specification table. Read before Phase 1."

* "document_references/skill-configuration.md": "Optional. Defines the skill-config.md a team places at its project root to steer the build system, module proxy, test and race commands, build tags, CGO_ENABLED, toolchain manager, container and deployment vocabulary - without forking the skill. Includes the field reference and the precedence rules: configuration steers HOW and never widens scope, the declared Go version changes only through go.toolchain_bump, an observed fact beats a configured one, and no field can waive an exit criterion including the arm64 race run. Read before Phase 1 only if a skill-config.md is present."

* "document_references/skill-config.template.md": "Copyable template for the optional configuration. Teams copy it to skill-config.md at their own project root and fill in the shared (container / deployment / CI) and Go-specific preferences. Highlights the three fields that most change the outcome: build_tags, cgo_enabled and arm64_environment. Not read during a run; it is the authoring starting point."

* "scripts/go_arch_scan.sh": "Read-only static scan covering the deterministic parts of Phase 1: the two-pass Shape C detection, the cgo inventory with the standard library filtered out, x86-only #cgo flags in both the `// #cgo` and block-comment forms, build-constraint shapes per directory, unconstrained .s files, panicking fallbacks, amd64-gated test files, committed native artifacts by content, x86-hardcoded download URLs, --platform and GOARCH pins, GOAMD64, GoReleaser goarch, deployment descriptors, and the behavioral leads. Never writes inside the scanned tree and never runs the project's build. Degrades to a grep-only mode without the Go toolchain, in which every verdict is CHECK. Exit 0 clean / 1 findings / 2 not a Go project."

* "scripts/arm64_validate.sh": "Runs the Phase 3 build / vet / test / race matrix and writes the logs under graviton-validation/raw/ with the canonical names the reports cite. Detects whether it is on arm64 hardware and reports every check it cannot measure as NOT RUN rather than PASS - including the race criterion, which it refuses to satisfy under emulation. On a race report it also runs the x86 baseline comparison, because that is what decides whether the finding is 'never ran -race' or 'the weak memory model made it observable'. Writes only inside graviton-validation/ and keeps build output in a GOBIN outside the tree."

* "scripts/sync_power.sh": "Regenerates POWER.md from SKILL.md, preserving the Kiro frontmatter and replacing the body. Run it after editing SKILL.md so the two entry points cannot drift."

Not read during a run; it points humans at this index for the file map."
